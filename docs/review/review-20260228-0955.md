# Review Report

## 1) 摘要
当前代理的 compaction 已能“生成摘要并返回 compaction block”，但关键缺口是：未在入站消息链路实现“遇到最新 compaction 后裁剪历史”的语义，导致后续请求仍携带压缩前上下文，触发重复压缩循环。结合日志与官方/开源资料，根因更偏协议语义落地不完整，而非单点参数问题。

## 2) 问题清单

### 高

- `compaction` 语义未在请求转换阶段落地为“历史裁剪”，压缩结果被当作普通 assistant 文本追加，未替代旧历史  
  - 证据（代码）：
    - `convert_claude_to_openai` 顺序遍历并转换全部消息，没有在“最新 compaction block”处分割历史：`src/conversion/request_converter.py:146-175`
    - assistant 中 `compaction` block 仅被拼到 `text_parts`：`src/conversion/request_converter.py:290-293`
  - 证据（官方文档）：
    - Anthropic Context Management 说明：后续请求中 API 会以最新 `compaction` 为分界，丢弃其之前所有 block，仅保留该 block 及之后内容（见官方文档 “On subsequent requests ... drops all prior blocks”）。
  - 证据（日志）：
    - 一次 `Compaction (pause)` 后，下一次请求 input token 几乎不降：`logs/proxy_20260227.log:6074`（94813）→ `:6089`（95087）
    - `Compaction+response` 后同样未降：`:5560`（91530）→ 下一轮 `:5576`（92186）
  - 影响：压缩在协议层“形式成立、效果失效”，会反复触发 compaction，吞吐和延迟显著恶化。

- 自动 compaction 默认返回 `pause_after_compaction=true`，但大量请求并非客户端显式发起 compaction edit，导致 CLI 侧不一定进入“受控重建上下文”路径  
  - 证据（代码）：
    - 自动触发分支强制 `pause_after_compaction=True`：`src/core/compaction.py:57-64`
  - 证据（日志）：
    - 当天日志中 auto 触发远多于 client edit（`auto=21, client=2`），且问题时段主要是 auto 分支：`logs/proxy_20260227.log`（多处 `Compaction triggered (auto)`）
  - 影响：若 CLI 当轮未按 compaction workflow 运行，代理“只返回 compaction”不等于客户端一定会改写后续历史，容易形成“压缩-未生效-再压缩”。

### 中

- CLI 侧 compaction 能力触发条件与当前使用方式可能不匹配（模型名/headers/beta）  
  - 证据（日志）：
    - 请求模型为 `GLM-4.7-FP8`：`logs/proxy_20260227.log:6072,6087`，而非 Claude 官方模型名
  - 证据（官方网关文档）：
    - 需要正确处理/转发 `anthropic-version` 与 `anthropic-beta`，否则功能可能降级（Claude Code LLM Gateway 文档）
  - 证据（官方 Context Management 文档）：
    - 该特性需 beta 头；文档列出支持模型范围
  - 影响：CLI 可能不发送或不稳定发送 `context_management.edits`，使你当前路径主要落入“代理自触发压缩”。

- 观测字段不足，难以区分“CLI 没发 compaction 信息”与“代理没按 compaction 语义消费”  
  - 证据：
    - 现有 INFO 日志未记录入站 `context_management` 是否存在、是否收到 compaction block、裁剪前后 message/token 对比
  - 影响：问题定位依赖推断，验证周期长。

### 低

- compaction 摘要调用开销偏高且波动大，放大了“无效压缩”成本  
  - 证据（日志）：
    - 多次摘要生成耗时 100s~300s（例如 `:5567`, `:5845`, `:6083`）
  - 影响：不是根因，但在未闭环前会明显拖慢交互。

## 3) 修改建议

- 对应“高-1”：在入站转换增加 `compaction boundary` 归一化  
  - 规则：找到“最新 assistant.compaction block”，丢弃其前全部消息，仅保留该 block 及其后消息；再做 `convert_claude_to_openai` 与 token 计数。  
  - 兼容：按官方/SDK，`compaction.content` 允许 `string | null`（失败压缩 no-op），`null` 需当作无内容但仍是边界标记。

- 对应“高-2”：区分两种 compaction 模式并避免混用  
  - 模式 A（CLI 驱动）：仅当入站存在 `context_management.edits` 且触发时，按客户端 `pause_after_compaction` 执行。  
  - 模式 B（代理兜底）：若未收到 client edit，建议走“代理内 continue”路径（不依赖 CLI 重建），或明确以 server-side session 历史重写方式兜底，避免单纯返回 pause compaction。

- 对应“中-1”：确保 Claude Code 网关协商条件稳定  
  - 在代理日志中显式记录并透传（如适用）`anthropic-version`/`anthropic-beta`。  
  - CLI 侧优先使用 Claude 模型别名（如 sonnet/opus）并由代理映射到 GLM，避免直接把 `GLM-4.7-FP8` 暴露为 Anthropic 请求模型名（降低能力门控风险）。

- 对应“中-2”：补齐可观测性（先日志后改逻辑）  
  - 增加字段：`has_context_management`, `edit_count`, `has_compaction_block`, `pruned_messages`, `tokens_before_prune`, `tokens_after_prune`。  
  - 这样能快速验证“CLI是否发送了压缩信号”与“代理是否正确消费了压缩边界”。

- 对应“低”：在闭环未完成前降低 compaction 成本  
  - 使用更快/更便宜 compaction 模型；限制 `COMPACTION_MAX_TOKENS`；必要时调高 `COMPACTION_TRIGGER_RATIO`，减少无效压缩触发频率。

## 4) 一致性校验（文档 + 代码）

- 一致项：
  - 代码已支持 `context_management.edits` 解析与 `stop_reason="compaction"` 返回：`src/core/compaction.py`, `src/core/constants.py`, `src/conversion/response_converter.py`。

- 不一致项（关键）：
  - 官方语义要求“后续请求以最新 compaction 为边界裁剪历史”，当前代码未实现该边界裁剪，仅将 compaction 当普通文本合并。  
  - 文档宣称“返回 compaction 后继续对话可用”，但日志显示 token 基本未下降，行为与预期不一致：`logs/proxy_20260227.log:6074,6089`、`:5560,5576`。

## 5) 风险/待确认点

- 可能未穷尽：当前依据单日日志与现有代码路径，未抓到完整原始入站 JSON（特别是 `context_management` 与 compaction block 的实到情况），结论存在“需二次抓包确认”的边界。
- 待确认：
  - 当前 Claude Code CLI 版本与配置是否开启/允许 context management beta。
  - CLI 是否在 compaction 后实际回传了 compaction block（若回传，代理边界裁剪缺失是主因；若未回传，需先解决能力协商/触发条件）。
