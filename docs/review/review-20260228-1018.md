# Review Report

## 1) 摘要
结合代码、2026-02-27 日志与官方文档，本问题的主因已基本收敛：代理当前实现了“生成 compaction 摘要”，但没有完整实现“后续请求按 latest compaction 边界裁剪历史”的协议语义；同时 `/v1/messages/count_tokens` 仍是粗估口径，极可能导致 Claude Code CLI 侧 compaction 触发不足。结果是：proxy 在压缩，CLI 仍按压缩前历史继续。

## 2) 问题清单

### 高

- 缺少 `latest compaction boundary` 历史裁剪语义（核心）
  - 代码证据：
    - 全量遍历历史消息转换，无“遇到最新 compaction 后丢弃之前历史”的逻辑：`src/conversion/request_converter.py:146-175`
    - `compaction` block 被直接并入 assistant 文本：`src/conversion/request_converter.py:290-293`
  - 官方协议证据：
    - Context Management 文档明确：后续请求应以最新 `compaction` block 为边界，丢弃其前内容，仅保留该 block 及之后消息。
  - 运行证据（2026-02-27）：
    - compaction 后下一轮请求 `input_tokens` 基本不降：`logs/proxy_20260227.log:6074 -> 6089`，`5560 -> 5576`。

- `/v1/messages/count_tokens` 与主链路 token 口径严重不一致（高概率导致 CLI 自身 compaction 不触发）
  - 代码证据：
    - 当前仅按 `chars/4` 粗估，未计 tools schema，未复用主链路 tokenizer/factor：`src/api/endpoints.py:421-447`
    - 主链路实际使用 GLM tokenizer + `TOKEN_ESTIMATE_FACTOR` + tools 计数：`src/conversion/request_converter.py:230-235`，`src/api/endpoints.py:88-93`
  - 协议背景证据：
    - Claude Code Gateway 要求实现 `/v1/messages` 与 `/v1/messages/count_tokens`；计数不准会直接影响客户端上下文管理决策。

### 中

- compaction 数据模型与官方 beta 类型仍有兼容缺口
  - 代码证据：
    - `compaction.content` 仅允许 `str`：`src/models/claude.py:23-27`
  - 官方 SDK/文档证据：
    - `compaction.content` 允许 `string | null`（当压缩失败时作为 no-op 占位），并建议继续保留该边界语义。

- auto compaction 与 CLI-managed compaction 混用，行为路径不稳定
  - 代码/日志证据：
    - auto 分支默认 `pause_after_compaction=True`：`src/core/compaction.py:57-64`
    - 当天日志 auto 触发远多于 client edit（`auto=21, client=2`），问题区间主要由 auto 路径触发。
  - 影响：
    - 在 CLI 未稳定进入其 context-management 流程时，proxy“只返回 compaction”并不等于客户端会重建历史。

### 低

- 可观测性不足，难以快速归因
  - 当前缺少关键日志字段：入站是否含 `context_management`、是否含 compaction block、裁剪前后 token 对比。

## 3) 修改建议（先方案，后改造）

- P0：先统一协议语义（必须）
  - 入站消息处理新增“latest compaction boundary 裁剪”规则：找到最后一个 `assistant.compaction`，丢弃其前所有 message blocks，仅保留该点之后历史。
  - `compaction.content` 模型改为可空（`str | None`）并按 no-op 语义兼容处理。

- P0：统一 token 计数口径（必须）
  - `/v1/messages/count_tokens` 复用主链路同一套计数逻辑（messages + tools + factor），避免 CLI 触发阈值判断失真。

- P1：明确单一压缩策略（推荐）
  - 优先“CLI-managed”路径：当收到 `context_management.edits` 时严格按客户端 edit 执行。
  - proxy auto 仅作为兜底，且避免与 pause 语义混用造成循环。

- P1：补足观测字段（推荐）
  - 每次请求记录：`has_context_management`、`edit_count`、`has_compaction_block`、`pruned_messages`、`tokens_before_prune`、`tokens_after_prune`。
  - 便于判断“CLI 没触发”还是“proxy 没消费”。

- P2：上线前验证矩阵（推荐）
  - Case A：CLI 发送 client edit + pause=true；下一轮 `input_tokens` 应明显下降。
  - Case B：client edit + pause=false；当轮完成后下一轮应仍保持压缩后 token 水位。
  - Case C：compaction `content=null` no-op；请求不应 4xx。
  - Case D：大 tools schema；CLI 触发时机与主链路 `effective_input` 收敛。

## 4) 一致性校验（文档 + 代码）

- 一致：
  - 已支持 compaction block 返回、`stop_reason="compaction"`、SSE compaction 事件。

- 不一致（关键）：
  - 官方“后续请求边界裁剪”语义未落地到请求转换链路。
  - 官方/SDK 对 `compaction.content` 可空的约定，当前模型未兼容。
  - `/count_tokens` 与主链路口径明显分叉。

## 5) 风险/待确认点

- 可能未穷尽：当前日志未完整打印入站 `context_management` 与 compaction blocks 原文，需补观测后二次确认。
- 待确认：
