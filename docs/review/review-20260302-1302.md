# Review Report

## 1) 摘要
本次审查聚焦 Claude Code compaction 回传链路（请求裁剪、SSE 转换、usage 结构）与 Anthropic 官方协议一致性。结论是：压缩本身已触发且摘要已生成，但当前实现在 `summary` 为空时仍执行边界裁剪，能够直接导致历史上下文丢失；同时 usage 字段与官方约定存在偏差。

## 2) 问题清单

### 高
- `summary` 为空/缺失时仍然执行 compaction 边界裁剪，导致大段历史消息被直接丢弃。
  - 证据：`src/conversion/request_converter.py:140-156` 的 `_prune_messages_at_boundary` 不区分 `summary` 是否有效，统一 `messages[boundary_index:]`。
  - 证据：同文件 `src/conversion/request_converter.py:348-351` 明确把 `null content` 当作 no-op（不注入摘要文本），但仍已完成历史裁剪，形成“裁剪生效、摘要缺失”的最坏组合。
  - 影响：与你日志一致，出现 `summary=null (no-op)` 且 `dropped 103/...` 后，旧上下文不可恢复。

- 对客户端 compaction 摘要回传“全信任”，缺少服务端保护性降级。
  - 证据：`src/conversion/request_converter.py:171-173` 只要找到 compaction block 就立即裁剪；没有“摘要非空校验”或“回退到不裁剪”的保护。
  - 证据：`src/api/endpoints.py:183-185` 有 tools 时强制上游 non-streaming，再由 `src/conversion/response_converter.py:698-769` 伪流式输出。该链路中若客户端对 `compaction_delta` 兼容性不完整，就可能只回传边界不回传摘要。
  - 影响：一旦客户端侧未正确持久化 `compaction_delta`，服务端会在下一轮继续执行危险裁剪。

### 中
- compaction 场景下 `usage.output_tokens` 统计口径与官方文档不一致。
  - 证据：`src/core/compaction.py:270-273`、`src/conversion/response_converter.py:1006-1009` 将 compaction 输出 token 累加进顶层 `usage.output_tokens`。
  - 官方文档：顶层 input/output token 不应包含 `usage.iterations` 里的 compaction token（应仅统计本次 message iteration）。
  - 影响：可能影响客户端预算/阈值判断与观测一致性。

- 缺少 compaction 回归测试，尤其是“compaction+response 经 SSE 后再回传”的闭环测试。
  - 证据：`tests/` 下无 compaction 相关测试（仅基础 API 示例）。
  - 影响：该类兼容问题难以及时发现，容易回归。

## 3) 修改建议
- 对应高-1：在 compaction boundary 裁剪前增加保护条件：仅当 `summary` 为非空字符串时才裁剪；否则记录 warning 并跳过裁剪（fail-open，避免历史丢失）。
- 对应高-2：增加协议兼容与可观测性。
  - 兼容：`ClaudeContentBlockCompaction` 增加解析兜底（例如兼容 `summary`/`text` 字段映射到 `content`，若客户端有历史差异可自动吸收）。
  - 观测：记录收到的 compaction block 内容长度、边界索引、是否为空字符串/None，便于快速区分“协议缺失 vs 客户端丢失”。
  - 运行策略：提供开关，允许 auto-compaction 改为 `pause_after_compaction=true`（由客户端按 stop_reason=compaction 继续），作为兼容模式回退方案。
- 对应中-1：按官方口径修正顶层 usage 统计（顶层仅 message iteration；compaction 放在 `usage.iterations`）。
- 对应中-2：补充 3 组测试：
  - `summary` 为空时不裁剪。
  - compaction+response 的 non-streaming->SSE->回传闭环。
  - usage 顶层与 iterations 口径校验。

## 4) 一致性校验（文档 + 代码）
- 官方要求“后续请求必须带回 compaction block 的 `content` 摘要，服务端再忽略该块之前历史”；当前实现在 `content` 缺失时仍忽略历史，和协议安全预期不一致。
- 官方要求 streaming 时处理 `content_block_delta` 的 `compaction_delta`；当前服务端已发送该事件，但缺少服务端侧防护来兜住客户端兼容差异。
- 官方要求顶层 usage 不含 compaction iteration token；当前实现未对齐。

## 5) 风险/待确认点
- 本次无法直接抓到 Claude Code 实际回传 JSON 原文（仅有代理日志），因此“为何 `content` 丢失”在客户端侧仍需一次抓包/请求体日志确认。
- 以上结论覆盖了代理 compaction 主链路，但不包含第三方前置网关对 SSE 的二次改写风险；若部署链路中有反向代理，需额外核查是否会改写 SSE 事件。
