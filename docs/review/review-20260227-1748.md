# Review Report

## 1) 摘要
最新改动已覆盖主要根因：`_input_tokens` 现包含 tools schema，compaction 判定改用 effective_input，显著降低再触发 400 的概率。仍有少量一致性风险，集中在计数口径分叉与估算兜底策略保守性。

## 2) 问题清单
### 中
- `/v1/messages/count_tokens` 仍用字符/4 粗估，口径与主请求路径的 GLM tokenizer + factor 明显不一致，客户端若依赖该接口做截断/compaction 决策，仍可能低估。见 `src/api/endpoints.py:417-447`。
- tools 计数的兜底分支 `len(json)//3` 在极大/深层 schema 时可能继续低估（未加安全系数），与主路径的 1.30 factor 口径不同，存在极端低估风险。见 `src/conversion/request_converter.py:15-37`（主计数）与新 `count_tools_tokens` fallback `//3`（同文件）。

### 低
- `count_tools_tokens` 未计入顶层 `type` 字段及少量结构开销（仅加了固定 4），对结果影响有限，但口径上与 messages 侧“按字段逐个 encode”不完全一致。见 `src/conversion/request_converter.py:15-37, 74-109`。

## 3) 修改建议
- 复用同一计数器于 `/v1/messages/count_tokens`：调用 `count_message_tokens` + `count_tools_tokens` + factor，避免客户端与服务端口径分叉。
- 在 `count_tools_tokens` 的 fallback 增加保守系数或直接复用主 tokenizer，必要时对 tools 另加 `tools_safety_margin`（可配置），防极端 schema 低估。
- 可选：在 `count_tools_tokens` 中计入顶层 `type`/结构开销，保持与 message 计数口径一致（影响小）。

## 4) 一致性校验
- tools token 计入、compaction 使用 effective_input 与 `docs/troubleshooting.md`/`.env.example` 描述一致。
- clamp 逻辑、provider cap 与代码实现一致。

## 5) 风险/待确认点
- 未做集成回放；建议用先前失败样本验证（含大量 tools schema 的请求），对比 `effective_input/allowed/final_max_tokens` 与上游 usage，确认误差收敛。
