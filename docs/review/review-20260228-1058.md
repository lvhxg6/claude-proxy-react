# Review Report

## 1) 摘要
本次改动方向正确，`compaction boundary` 裁剪与 `compaction.content` 可空兼容都已落地，核心闭环比之前明显完善。  
但仍有 2 个关键缺口会影响你目标（让 Claude Code CLI 端稳定按压缩后上下文继续）：`count_tokens` 与主链路阈值口径仍不一致、compaction 触发时摘要仍基于未裁剪历史构建。

## 2) 问题清单

### 高

- `/v1/messages/count_tokens` 仍未对齐主链路的 `TOKEN_ESTIMATE_FACTOR`，CLI 触发阈值判断仍可能失真  
  - 证据：
    - 主链路 compaction 判定使用 `effective_input = ceil(raw * TOKEN_ESTIMATE_FACTOR)`：`src/api/endpoints.py:103-105`
    - `count_tokens` 返回的是 `convert_claude_to_openai` 的 `_input_tokens`（raw），未乘 factor：`src/api/endpoints.py:447-450`
  - 影响：
    - CLI 可能低估上下文使用率，导致 CLI 侧 compaction 仍不触发或触发偏晚。

- compaction 触发时，摘要请求仍基于“未裁剪原始请求”构建，可能把已失效历史再次纳入摘要  
  - 证据：
    - compaction 入口传入的是原始 `request`：`src/api/endpoints.py:126-129`
    - `_handle_compaction` 直接对该 `request` 调用 `build_compaction_messages`：`src/api/endpoints.py:300`
    - `build_compaction_messages`/`_serialize_messages` 遍历 `request.messages` 全量历史：`src/core/compaction.py:70-107`
  - 影响：
    - 当请求中已存在 compaction boundary 时，摘要仍可能重复吸收 boundary 前历史，增加延迟和 token 成本，并污染“最新压缩上下文”语义。

### 低

- 自动化测试未覆盖本次关键逻辑（当前 pytest 全部跳过）  
  - 证据：
    - `pytest -q` 输出 `13 skipped`（缺少 async 插件），未对 compaction 路径形成回归保护。

## 3) 修改建议

- 对齐 `count_tokens` 口径  
  - 返回值改为与主链路判定一致（至少可选返回 effective 计数，或新增字段区分 `raw_input_tokens`/`effective_input_tokens`）。

- compaction 摘要输入改为“裁剪后历史”  
  - 在 compaction 触发路径中复用 boundary 裁剪结果（不要再用未裁剪 `request` 序列化摘要语料）。

- 增加最小回归用例  
  - 用例 1：含历史 compaction block 的请求，验证摘要构建不包含 boundary 前消息。  
  - 用例 2：`count_tokens` 与主链路 compaction 判定口径一致性（raw/effective 的契约明确）。

  - compaction 后下一轮 `has_compaction_block=True` 且 `input_tokens` 明显下降；
  - CLI 侧不再反复提示 `Context limit reached`.
