# Review Report

## 1) 摘要
本次修复已明显提升稳健性：引入 `TOKEN_ESTIMATE_FACTOR`、动态 `safety_margin`、`MAX_OUTPUT_TOKENS` 三重 clamp，并将 compaction 检查前置，已覆盖你们前面定位到的大部分主路径问题。\
但从代码一致性看，仍存在“本地 token 低估导致偶发 400”的残余风险，主要集中在 tool schema 计数遗漏与计数口径不一致。

## 2) 问题清单
### 高
1. `input_tokens` 估算未包含顶层 `tools/tool_choice/stop` 等请求字段，tool-heavy 场景仍可能低估并触发上游 400。\
   - 证据：`count_message_tokens()` 仅接收并统计 `messages` 内容与消息内字段（`role/content/name/tool_calls/tool_call_id`），未统计顶层工具定义。见 `src/conversion/request_converter.py:12-60`。\
   - 证据：`openai_request["tools"]` 在后续才挂载；最终 `_input_tokens` 仍来自 `count_message_tokens(openai_messages, ...)`。见 `src/conversion/request_converter.py:162-177` 与 `src/conversion/request_converter.py:195-196`。\
   - 风险：工具 schema 很大时（尤其多工具、深层 JSON Schema）会显著抬高上游 prompt tokens，当前 clamp 可能仍偏松。

### 中
1. `/v1/messages/count_tokens` 与主请求路径使用不同计数逻辑，返回值偏差可能误导客户端上下文管理策略。\
   - 证据：该接口仍使用“字符数/4”粗略估算。见 `src/api/endpoints.py:417-447`。\
   - 风险：客户端若依赖此接口做 compaction/截断决策，可能在高占用时仍判断“可继续”。

2. compaction 触发判定使用 `raw input_tokens`，未使用 `effective_input`，在低估场景会延后触发。\
   - 证据：`should_compact(request, input_tokens)` 传入的是 raw 值。见 `src/api/endpoints.py:104`。\
   - 证据：compaction 判定直接比较 `input_tokens >= trigger_value`。见 `src/core/compaction.py:45`。\
   - 风险：虽已前置 compaction 检查，但触发阈值仍可能因低估而“该压缩时未压缩”。

### 低
未发现明显低优先级一致性问题。

## 3) 修改建议
1. 对应高优先级问题：将 `_input_tokens` 估算扩展为“完整 payload 级别”计数。至少纳入：`tools`、`tool_choice`、`stop`、`response_format`（若有），并与上游协议字段保持一致。若短期难以做到精确，建议对含 `tools` 的请求额外叠加可配置保守因子。 
2. 对应中优先级问题（count_tokens）：复用主路径同一计数器和同一修正因子，避免两个口径长期漂移。 
3. 对应中优先级问题（compaction）：将 compaction 触发判定改为基于 `effective_input`，或允许配置 `compaction_trigger_factor`，确保在已知低估模型上更早触发。

- `.env.example` 新增变量与代码读取逻辑一致。
